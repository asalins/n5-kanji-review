## 1. หลักการ: ReviewLog เป็นความจริง ส่วน ReviewCard คำนวณจาก log (D3, D4)

- สิ่งที่ sync มีแค่ **ReviewLog** (เหตุการณ์ที่เพิ่มอย่างเดียวและไม่ถูกแก้) กับ **UserSettings** ไม่ sync ReviewCard โดยตรง
- ReviewCard ในแต่ละเครื่อง**คำนวณใหม่จาก log** ด้วย `srsV1`:
  - ใช้ `createNewCard(item, mode, เวลาของ log แรก)` แล้วตามด้วย `updateCardState` ทีละ log
  - เรียง log ตาม `reviewedAt` และถ้าเวลาเท่ากันให้เรียงตาม `id`
  - ทำแบบนี้แล้วสองเครื่องที่มี log ชุดเดียวกันจะได้ card เหมือนกันทุกช่อง โดยไม่ต้องใช้ `lastReviewed` หรือ `reviewCount` ตัดสินว่าใครถูก (ตรงตาม D4)
- **ต้องพิสูจน์ก่อน (L3a):** card ที่ได้จากการคำนวณจาก log ต้องเท่ากับ card ที่เก็บไว้ทุกช่อง (interval, due, ease, state และ count) ทดสอบกับ
  - log สุ่มหลายพันชุด (property test)
  - ไฟล์ backup จริงจาก Production
  - ข้อมูลที่ migrate มาจาก v2
- **ถ้าพิสูจน์ไม่ผ่านกับข้อมูลเก่าบางส่วน** (เช่น card ที่มาจาก import แต่ไม่มี log ครบ) card นั้นถูกทำเครื่องหมายเป็น "base" ใช้ค่าที่เก็บไว้เป็นจุดเริ่มต้น แล้วคำนวณต่อเฉพาะ log ที่ใหม่กว่า `lastReviewed` ของ card กรณีนี้จะรายงานจำนวนให้ Gate ตัดสินก่อน L3b
- **ข้อจำกัดที่ต้องบันทึก:** ลำดับเวลามาจากนาฬิกาของแต่ละเครื่อง ถ้าสองเครื่องทบทวน card ใบเดียวกันขณะออฟไลน์ในเวลาใกล้กันกว่าที่นาฬิกาคลาดกัน ลำดับที่ใช้คำนวณอาจไม่ตรงกับลำดับจริง ผลยังเป็นสถานะ SRS ที่ถูกต้องตามลำดับเหตุการณ์ที่ใช้ และไม่มี log ใดหาย
- ID ชน (D3): ใช้ `mergeReviewLogs` จาก L1 ทุกครั้งที่รวม log จาก Cloud กับในเครื่อง log ใหม่เป็น `log:<uuid>` จึงไม่ชนกันอยู่แล้ว ส่วน log เดิม `cardId#n` ใช้ตัว resolver จัดการ
- ไม่ sync StudySession (เป็นประวัติของแต่ละเครื่อง) สถิติและ streak คำนวณจาก log จึงตรงกันเอง

## 2. โครงสร้าง Firestore (D7)

```
users/{uid}                      { schema: 1, epoch: n, resetAt: ts|null, createdAt: ts }
users/{uid}/logs/{logId}         { ...ReviewLog 10 fields, epoch: n, uploadedAt: serverTimestamp }
users/{uid}/meta/settings        { ...UserSettings, uploadedAt: serverTimestamp }
```

- **1 log = 1 document** (~300 bytes) ไม่มีทางถึงขีดจำกัด 1 MiB และไม่มีหลายเครื่องเขียนเอกสารเดียวกันพร้อมกัน (ต่างจากแบบ `logDays/{date}` ที่ D7 ปฏิเสธไว้)
- `logId` ใช้เป็น document id จึง**ส่งซ้ำได้โดยไม่เกิดข้อมูลซ้ำ** เพราะเขียนแบบ create-only ถ้ามี document นี้อยู่แล้วก็ไม่ทำอะไร
- Settings ใช้กติกา **"ใครใหม่กว่าชนะ"** โดยเทียบ `updatedAt` และถ้าเท่ากันให้เก็บของเครื่องนี้ไว้ ใช้กติกานี้กับ settings เท่านั้น (D5) และระบุว่าไม่ใช่หลักฐานลำดับเวลาที่แน่นอน
- **โควตาแผน Spark (D12):**
  - 1 การทบทวน = 1 write
  - การดึงข้อมูลใช้ query `uploadedAt > cursor` จึงอ่านเฉพาะของใหม่
  - ดึงครั้งแรกอ่านเท่ากับจำนวน log ทั้งหมด
  - ถ้าเกินโควตา (`resource-exhausted`) sync จะหยุดชั่วคราวและแสดง "sync หยุดชั่วคราว" ข้อมูลในเครื่องไม่ได้รับผลกระทบ แล้วลองใหม่วันถัดไป

## 3. Security Rules (D8)

- ปฏิเสธทุกอย่างเป็นค่าเริ่มต้น และ `request.auth.uid == uid` เท่านั้นที่เข้าถึง `users/{uid}/**` ได้
- `logs`:
  - **create** ได้เฉพาะเมื่อ schema ถูกต้องครบ 10 field บวก `epoch` และ `uploadedAt` และขนาดไม่เกินที่กำหนด
  - `epoch` ต้องเท่ากับ `get(users/{uid}).epoch` เพื่อกันเครื่องที่ยังไม่รู้เรื่อง reset ส่งข้อมูลเก่าขึ้นมา (D6)
  - **update ห้าม**
  - **delete** ได้เฉพาะเจ้าของ (ใช้ตอน reset และ Delete Account)
- `users/{uid}`: `epoch` เพิ่มขึ้นได้ทีละ 1 เท่านั้น ห้ามลด
- `meta/settings`: schema ต้องถูกต้อง และ `updatedAt` ต้องเป็นตัวเลขที่ไม่ติดลบ
- test (ด้วย `@firebase/rules-unit-testing`):
  - ผู้ใช้อื่นอ่านหรือเขียนไม่ได้
  - ผู้ที่ไม่ล็อกอินทำอะไรไม่ได้
  - update log ไม่ได้
  - ส่ง log ด้วย epoch เก่าไม่ได้
  - ลด epoch ไม่ได้
  - ส่งข้อมูลผิด schema หรือ field เกินไม่ได้
  - ลบข้อมูลของตัวเองได้

## 4. การทำงานของ Sync (D9) และการแก้ L-1

**L-1 ต้องปิดก่อนเปิด sync:**
1. **Sync ไม่ใช้ `accountHint` และไม่ใช้สถานะที่ UI แสดงเลย** จะเริ่มได้ก็ต่อเมื่อ `auth.currentUser` มีอยู่, `getIdToken()` สำเร็จ และ**คำขอแรกไปยัง Firestore สำเร็จ** (ถือเป็นการยืนยันกับเซิร์ฟเวอร์) ทุกครั้งที่ส่งข้อมูลจะใช้ token ของ Firebase ซึ่ง Rules ตรวจอีกชั้น
2. **แก้ UI (ตามที่เสนอใน L2):** ตอนเปิดแอปแล้วพบ session เดิม ให้แสดง `checking` จนกว่าเซิร์ฟเวอร์จะตอบ ถ้าเกิน 10 วินาทีหรือได้ error ด้านเครือข่าย ให้เปลี่ยนเป็น `signed-in-offline` และฟัง event `offline` ด้วย จะได้ไม่มีสถานะใดที่ดูเหมือน "ยืนยันแล้ว" โดยที่เซิร์ฟเวอร์ยังไม่ได้ตอบ
3. มี unit test และ E2E ของ 3 กรณีนี้

**ตารางสถานะของ Sync:**

| เหตุการณ์ | การทำงาน |
|---|---|
| ออฟไลน์ | ไม่ sync เก็บรายการที่ยังไม่ได้ส่งไว้ใน outbox ใช้แอปได้ตามปกติ |
| token หมดอายุ | SDK refresh ให้เอง ถ้าได้ error ด้านบัญชี ให้หยุด sync แล้วเข้ากติกา C1 (ออกจากระบบพร้อมข้อความ) **ข้อมูลในเครื่องไม่ถูกแตะ** |
| บัญชีถูกลบ | เหมือนกรณีข้างบน: หยุด sync และไม่ลบข้อมูลในเครื่อง |
| เครือข่ายกลับมา | event `online` → ตรวจกับเซิร์ฟเวอร์ → ส่งรายการค้าง → ดึงของใหม่ |
| quota หมด | หยุดชั่วคราว แล้วลองใหม่ตามรอบ |

- **จังหวะ sync:**
  - หลังเปิดแอป (เมื่อตรวจกับเซิร์ฟเวอร์ผ่านแล้ว)
  - หลังทบทวนเสร็จ (รอ 30 วินาทีเพื่อรวมหลายรายการ)
  - เมื่อเกิด event `online`
  - เมื่อหน้าแอปถูกซ่อน (ส่งรายการค้างทันที)
- **ป้องกัน sync ซ้อนกัน:** ใช้ Web Locks API (`navigator.locks`, ชื่อ `n5-sync`) จึงมีแท็บหรือ PWA เดียวที่ sync ได้ในแต่ละครั้ง (เบราว์เซอร์เป้าหมายรองรับทั้งหมด)
- **ลองใหม่:** ใช้ backoff 30 วินาที, 2 นาที, 10 นาที, สูงสุด 1 ชั่วโมง
- **การผูกบัญชีกับเครื่อง:** ครั้งแรกที่ล็อกอินบนเครื่องที่มีความคืบหน้าอยู่แล้ว จะถามก่อนว่า "**อัปโหลดความคืบหน้าในเครื่องนี้เข้าบัญชี X?**" ถ้าข้อมูลในเครื่องผูกกับบัญชี A แล้วมีบัญชี B ล็อกอิน **จะไม่อัปโหลดข้อมูลของ A เข้า B** และให้เลือกระหว่าง ไม่ sync หรือ Reset แล้วดึงข้อมูลของ B ลงมา

## 5. Reset, Import และการลบ (D6, D-L2-6)

- **Reset progress** เมื่อ sync เปิดอยู่:
  1. เพิ่ม epoch ใน transaction
  2. ลบ log ของ epoch เก่าบน Cloud ทีละ batch (batch ละไม่เกิน 500)
  3. ล้างข้อมูลในเครื่อง
- ถ้าขั้นใดล้มเหลว จะบันทึก "reset ค้าง" ไว้ในเครื่อง และ**หยุด sync ทั้งหมด**จนกว่าจะทำสำเร็จ
- **เครื่องที่ยังไม่รู้เรื่อง reset:** เมื่อกลับมาออนไลน์และพบว่า epoch บน Cloud สูงกว่าที่รู้
  1. **ไม่อัปโหลดอะไรเลย** (Rules ก็ปฏิเสธอยู่แล้ว)
  2. แจ้งว่า "ความคืบหน้าถูก reset จากอุปกรณ์อื่นเมื่อ …"
  3. รายการที่ยังไม่ได้ sync จะถูก**เก็บไว้ในเครื่องเป็นสำเนา** ให้ export เป็นไฟล์ได้ก่อนล้าง **ไม่มีการลบเงียบๆ และไม่ฟื้นข้อมูลที่ถูก reset แล้วกลับขึ้น Cloud**
- **Import (Replace)** เมื่อ sync เปิดอยู่: ถือเป็น reset ที่มีข้อมูลใหม่ตามมา
  1. แทนที่ข้อมูลในเครื่องใน transaction เดียว (เหมือนเดิม)
  2. เพิ่ม epoch และลบ log เก่าบน Cloud
  3. อัปโหลด log จากไฟล์ด้วย epoch ใหม่
  - ถ้าขั้นที่ 2 หรือ 3 ล้มเหลว จะเก็บสถานะ "ค้าง" ไว้แล้วทำต่อภายหลัง ข้อมูลในเครื่องคือข้อมูลที่ import แล้ว (dialog แจ้งผลให้ชัดว่าเป็นแบบนี้)
- **Delete Account (D-L2-6):** ยืนยันตัวตนใหม่ → **ลบข้อมูลบน Cloud ทั้งหมด** (logs, meta และ users/{uid}) → ถ้าลบ Cloud ไม่สำเร็จให้**หยุด**โดยยังไม่ลบบัญชี → `deleteUser` → ลบข้อมูลในเครื่องถ้าผู้ใช้เลือก ข้อความแจ้งผลแยกตามจริงตามกติกา C2 และ `cloudData` เปลี่ยนจาก `none` เป็น `deleted` หรือ `failed`
- **หน้า Privacy** ต้องปรับก่อนเปิด sync ให้บอกว่ามีข้อมูลการเรียนบน Cloud แล้ว (ต้องผ่าน Gate)

## 6. การเปลี่ยนแปลงในเครื่อง: migration v4 (ต้องอนุมัติ)

- store ใหม่ `syncLedger` (คีย์เป็น logId → `{ epoch, uploadedAt }`) เก็บว่า log ใดอยู่บน Cloud แล้ว รายการที่ยังไม่ได้ส่ง = log ที่ไม่มีใน ledger
- store ใหม่ `syncMeta` (เก็บรายการเดียว) → `{ uid, knownEpoch, pullCursor, pendingReset, lastError }`
- **ไม่แก้** ReviewLog, ReviewCard หรือ store เดิมใดๆ ถ้า migration ล้มเหลว ฐานข้อมูลจะยังเป็น v3 (ใช้รูปแบบเดียวกับ v3 และทดสอบแบบเดียวกัน)
- backup ยังเป็น format 2 เพราะข้อมูล sync ไม่อยู่ใน backup

## 7. Emulator และเกณฑ์ PASS / BLOCKED

- **ข้อเท็จจริง:** Auth Emulator รันใน sandbox ได้ แต่ **Firestore Emulator รันไม่ได้** เพราะต้องดาวน์โหลด jar จาก `storage.googleapis.com` ซึ่งถูกบล็อก (ทดสอบแล้ว 2026-10-17)
- **ข้อเสนอ:** เพิ่ม GitHub Actions workflow `emulator-tests.yml` (Java 21 + firebase-tools ที่ pin เวอร์ชัน) รัน Rules tests, Sync integration tests และ Auth tests ทุกครั้งที่ push ไปที่ `l3-*` **ไม่ deploy อะไร** ทางเลือกคือรันบน PC ของเจ้าของโครงการ (ต้องติดตั้ง Java)
- **เกณฑ์:**
  - **PASS** = job ใน CI สำเร็จ และ log แสดงจำนวน test ที่ผ่าน
  - **BLOCKED** = ไม่มีผลจาก CI หรือ emulator ไม่พร้อม (test จะ fail ด้วยข้อความ BLOCKED เหมือน L2)
  - **ห้ามนับผลทดสอบด้วยมือหรือ unit test ที่ใช้ของปลอมแทน Emulator**
- **Sync integration tests (Emulator):**
  - สองเครื่องปลอมทบทวนแบบออฟไลน์แล้ว merge ได้ card เหมือนกันทั้งสองฝั่ง
  - ลำดับการ sync ไม่มีผลต่อผลลัพธ์
  - ส่งซ้ำแล้วไม่เกิดข้อมูลซ้ำ
  - legacy id ชนกันแล้วถูกเปลี่ยนชื่อและเก็บไว้ทั้งสองรายการ
  - reset แล้วเครื่องที่ยังไม่รู้ส่งข้อมูลเก่าขึ้นมาไม่ได้
  - import ซ้ำ
  - Delete Account ลบข้อมูล Cloud ครบก่อนลบ Auth
  - quota error ถูกจำลองแล้วหยุดชั่วคราว
  - การแยกข้อมูลระหว่างผู้ใช้

## 8. แผนทดสอบอื่น

- unit:
  - replay (property test + ข้อมูลจริง)
  - outbox และ ledger
  - backoff และ lock
  - การผูกบัญชีกับเครื่อง
  - ตารางสถานะของ sync
  - การแก้ L-1
- migration v4 ใช้รูปแบบเดียวกับ v3 (ทุก store เหมือนเดิม และกรณีล้มเหลว DB ยังเป็น v3)
- E2E ผู้ที่ไม่ล็อกอินต้องไม่มี request ไป Firebase เลย (เงื่อนไขเดิมของ L2 ยังต้องผ่าน)
- `verify:all`, account isolation และตรวจว่า build ของ Production ตรงกับ baseline ทุก byte
- **ทดสอบด้วยมือ 2 เครื่องจริง** (PC + Android) เป็นงานของ L4 ใน L3b จะทดสอบเฉพาะ smoke บน Preview

| D-L3-1 | ข้อมูลที่ sync | sync เฉพาะ log และ settings ส่วน card คำนวณใหม่จาก log (ต้องพิสูจน์ใน L3a) |
| D-L3-2 | โครงสร้าง Firestore | 1 log ต่อ 1 document, `users/{uid}/logs/{logId}` และเขียนแบบ create-only |
| D-L3-3 | Reset และ Import | ใช้ epoch ที่ Rules บังคับ เครื่องที่ยังไม่รู้เรื่อง reset จะเก็บสำเนาในเครื่องและไม่อัปโหลด |
| D-L3-4 | L-1 | sync ต้องผ่านการยืนยันกับเซิร์ฟเวอร์ก่อน และแก้ UI ให้ไม่แสดง signed-in ก่อนเซิร์ฟเวอร์ตอบ |
| D-L3-5 | Emulator | ใช้ GitHub Actions (เพิ่ม workflow ใหม่ ไม่ deploy อะไร) |
| D-L3-6 | Migration v4 | เพิ่ม `syncLedger` และ `syncMeta` ไม่แก้ store เดิม |
| D-L3-7 | ขั้นตอน | แบ่งเป็น L3a และ L3b แต่ละขั้นมี Gate ของตัวเอง |
| D-L3-8 | การผูกบัญชี | ถามก่อนอัปโหลดข้อมูลในเครื่องเข้าบัญชี และไม่อัปโหลดข้ามบัญชี |

## 10. ส่งมอบ

- **L3a:** rules, emulator CI, ผลพิสูจน์ replay และรายงาน
- **L3b:** commit, bundle, checksum, `verify:all`, ผล Emulator จาก CI, หลักฐานว่า L-1 ปิดแล้ว และหลักฐานว่า Production ไม่เปลี่ยน

หลังส่งมอบแต่ละขั้นจะหยุดรอ Gate ส่วน L4 (ทดสอบหลายเครื่อง และขึ้น Production) ต้องผ่าน Gate แยก
